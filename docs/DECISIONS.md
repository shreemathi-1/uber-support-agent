# Decision log

Numbered, with evidence where it exists. Bootstrap-phase entries are marked; numbers from that phase are plumbing checks, not results.

1. **Built the pipeline on a provisional taxonomy and 12 placeholder help articles** so evaluation tooling existed before the manual data work. `taxonomy.py` intents and `AMOUNT_LIMIT`/`AUTO_ALLOW` are guesses; articles carry `date_checked: UNVERIFIED-PLACEHOLDER`. Replaced on <date>.
2. **Cache key = SHA-256(model + json.dumps(messages, sort_keys=True))** (session 1). Sorted keys so dict ordering in a prompt builder cannot cause a spurious miss. Sampling params (temperature, max_tokens) are deliberately *not* in the key: they are fixed per stage, so the model + messages already identify the call. Revisit if a stage ever varies them.
3. **`cached_llm` takes `call_fn(model, messages)`** rather than a zero-arg closure, so the network function is a plain importable function that can be swapped for a fake in tests.
4. **`DB_PATH` env var (default `data/app.db`)**, read at call time, not import time, so tests point it at a temp file without reloading modules.
5. **Session 1 ran on Python 3.14 (`.venv`)** although the stack pins 3.11. Pinned wheels in `requirements.txt` target 3.11; the Dockerfile will use `python:3.11-slim`. Flagged, not yet resolved.
6. **Golden-set sampling unit is a customer turn, not a thread root** (session 2). No root tweet in the data replies to anything (checked: 0 of 40,886), so a literal "history if the root is a follow-up" would leave the history column empty for all rows and make `is_repeat_contact` unlabellable. Candidates are the root turn (history empty) and the second customer turn (history = root), one row per thread; follow-ups therefore appear in natural proportion. Tweet ids for follow-up turns are recovered from `uber_tweets.csv` by (created_at, clean_text); 2 ambiguous keys are skipped.
7. **Both the sampled turn and its history turn are removed from the retrieval corpus.** Rule 4 only requires the sampled id, but leaving the root of the same thread in the corpus would let retrieval hand the drafter the customer's own earlier message.
8. **Keyword buckets are coverage steering only.** `driver_side` has 128 eligible roots, so the 15-minimum is reachable; the bucket name is never written to the CSV.
9. **Scripts run as modules (`python -m scripts.x`)** so they share helpers (`is_english`) without path hacks; `scripts/__init__.py` exists for that reason.
10. **`sample_golden.py` refuses to overwrite a golden set that has any label filled in.** `make data` reruns from scratch (split → sample → validate), so without this guard a rerun after labelling would wipe hand labels. With labels present it keeps the file and only re-applies the corpus removal. Tested: one label set, rerun, file byte-identical.
11. **Deflection regex widened after eyeballing the first split** (session 2 fix). Added: following up, be in contact, in-app support/messaging/help/message, send a note, reach this link, check this link, follow the link, for more info, learn more, more information. Informative share fell from 19.5% to 13.6% (7,301 pairs). Link-only replies ("visit here: for more") count as deflection because the link text was stripped and nothing answerable remains. Golden set was not resampled; corpus removal re-applied to the same 227 rows.
12. **validation.json reports two date ranges.** All Uber-related tweets span 2014-05-27 to 2017-12-03 because hop-2 extraction pulls in older customer tweets; Uber_Support-authored tweets span 2014-12-20 to 2017-12-03; that is the range to quote in the README (stats.json's Apr 2016 start came from a different subset and should be reconciled).
13. **Fallback responses are cached under the primary model's key** (session 3). `llm.groq_chat` falls back to `FALLBACK_MODEL` after 3 failed attempts, but the cache key was computed by the caller with `PRIMARY_MODEL`. Reproduction therefore replays whatever answered, and a warning is logged when the fallback fired. Acceptable for a cache; the eval report should note how many rows fell back if it is ever more than a handful.
14. **Invalid enrich responses are cached too.** The cache stores whatever the model returned; the retry appends the validation error to the user turn, which gives a different key. A message that once produced bad JSON costs one cache hit plus one retry lookup forever after, never an extra network call. Simpler than teaching the cache about validity.
15. **Enrich prompt wording** (session 3): urgency `high` covers stranded / safety / time-critical / angry repeat contact, `medium` any unresolved problem, `low` questions and feedback. `mentions_safety` and `mentions_legal` got one-line definitions each so the flags the rules depend on are not left to the model's judgement. History turns are rendered as `Earlier (<role>): ...` lines before `Message: ...`.
16. **Switched Groq models to `openai/gpt-oss-120b` (primary) and `openai/gpt-oss-20b` (fallback)** on 2026-09-12. Groq decommissioned `llama-3.3-70b-versatile` and `llama-3.1-8b-instant` on 2026-08-16 (console.groq.com/docs/deprecations). Judge unchanged (Gemini Flash-Lite, different family). `llm.groq_chat` gained an optional `reasoning_effort` (sent via `extra_body`, since the pinned groq SDK predates the typed parameter); enrich uses `"low"` because classification needs no long chain of thought and the free tier is token-limited. `scripts/check_models.py` probes both models with one json_mode call; both parsed on first try. Any enrich cache entries keyed on the old model ids are dead weight and can be ignored.
17. **Retrieval index shape** (session 4). Chroma cosine space, embeddings supplied by us (MiniLM, normalised) so Chroma never downloads its default ONNX model. `pairs` = all 7,268 informative pairs + a seeded sample of 12,732 deflection pairs (cap 20,000; 67 MB on disk, 88 s to build). `intent` metadata on pairs is the keyword bucket mapped onto Intent values: a retrieval hint, never a label. No bucket covers `policy_or_info_question`, so that intent always takes the unfiltered fallback.
18. **Fallback thresholds.** Unfiltered requery when the intent-filtered query returns fewer than 3 pairs (or 0 help chunks) or the best hit has cosine distance above 0.6. The 0.6 is a guess to revisit with `peek_retrieval.py` output; the drafter gets distances back so it can ignore a far help chunk.
19. **`Context` narrowed to `examples` + `facts`.** Retrieval returns only what it found; `run.py` will carry message, history and enrichment separately. `RetrievedPair.source` added so the drafter can prefer informative examples over deflection templates.
20. **Bucket regexes moved to `pipeline/buckets.py`** with the short names kept as keys, because `sample_golden` sorts buckets by name and renaming them would have changed the golden sample (verified byte-identical after the move).
21. **`posthog==5.4.0` pinned.** chromadb 0.6.3 calls `posthog.capture` with the pre-6.0 signature; with posthog 7.x every client and query call logged "Failed to send telemetry event" even with `anonymized_telemetry=False`. Pinning below 6 removes the noise without touching chromadb.
22. **Escalation reply references the tickets row id** (session 5). Every request writes a `tickets` row; an escalation adds an `escalations` row that points back via `ticket_id` and carries the draft (null when a rule fired first) and the retrieved ids. The customer-facing reference is the ticket id because it exists for every request; the queue view can show both.
23. **`check()` takes the usable facts.** The safety reviewer cannot judge "policy not supported by the facts" without them, so `check(message, draft, facts)` receives the same distance-filtered chunks the drafter saw. Any exception or unparseable JSON returns `(False, "check_error: ...")`, which run.py turns into `unsafe_draft`.
24. **Draft post-processing order:** strip URLs, collapse whitespace, prefix the repeat-contact line if the text does not already contain "again", then cut at 280 characters on the last sentence end. Prefix before cut so the cap holds. The "again" heuristic is crude and logged here so it can be replaced if the judge flags double apologies.
25. **Cache hit/miss counters are process-wide** (`cache.STATS`); run.py logs the per-request delta. Good enough for a log line, not for concurrency accounting.
26. **`AMOUNT_LIMIT` read from env at rule time** with `taxonomy.AMOUNT_LIMIT` as default, so the eval can sweep thresholds without editing code. `low_confidence` floor 0.7 is marked PROVISIONAL in `rules.py`; smoke runs show confidence clustering at 0.93-0.97, so this rule may rarely fire.
27. **Draft uses `reasoning_effort="low"` and `max_tokens=400`, not the planned None/160.** First live run: all three drafts came back as empty strings because gpt-oss spent the whole budget on reasoning and the reply never started. The checker (20B) also passed two of the empty drafts as safe. Fixes: `check()` returns `(False, "empty_draft")` before any LLM call, `cached_llm` never stores an empty completion, and the checker prompt names empty or truncated drafts as unsafe. Three poisoned cache rows were deleted by hand on 2026-09-12.
28. **`other` is auto-allowed with a canned reply and no LLM draft.** Escalating "thanks" wastes a specialist; drafting for a rant or spam invites the model to invent something. run.py answers with a fixed line and writes a normal tickets row (reason `auto`).
29. **Repeat-contact definition tightened** after the smoke run flagged "background check still pending, no update" as repeat contact: now only an explicit prior contact with no reply, or a prior customer turn in history. Waiting on a decision is not repeat contact.
30. **One identifier per intent.** `app_or_account_issue` asks only for the account email, `lost_item` only for the trip date. The drafter obeys the `ask_for` string literally, so two-part strings produced two-question replies.
31. **`RATE_SLEEP=0` in `.env` for the API; batch scripts call `llm.batch_mode()`** which raises it to 2 when it is 0. Eval, smoke, and suggest loops therefore never run the free tier flat out.
32. **`sample_golden.py --suggest`** writes the enricher's intent into `suggested_intent`, never `intent`. The labeller reads the text and agrees or overrides; the labelling note must say suggestions were shown, and the override rate is reported. The enrich calls are the same cache keys run_eval will use, so this also pre-warms the cache.
33. **Simple baseline silver-labels 1,000 pairs, not 2,000** (session 6). TF-IDF + logistic regression on eight classes saturates well before that, and 1,000 enrich calls is about 0.9M prompt tokens; spending twice that on a baseline undermines "simple". `--silver-n` overrides; the plumbing check used 200. Silver labels are the enricher's own predictions, so the baseline inherits its errors; the report must say so.
34. **`retrieved_ids` entries are `kind:id:distance`** (e.g. `help:lost_item#0:0.42`). The judge re-applies the drafter's 0.6 filter from these, so it scores against the facts the drafter actually saw without widening `ChatResponse`.
35. **Judge scores auto-handled replies only.** The escalation template is not a drafted reply; judging it would inflate or deflate the mean for no information. `mean judge total (n)` in summary.md shows the count.
36. **Reason breakdown counts true and false escalations per reason.** Precision per rule is what decides whether `low_confidence` (and the 0.7 floor) stays.
37. **Kappa buckets for judge vs human:** totals 5-25 split at low <= 12, mid 13-19, high >= 20. Chosen before any scores exist so the split cannot be tuned to the result.
38. **`simple_intent.pkl` is a convenience, not a dependency.** `load_or_fit` retrains from cached silver labels when the file is missing, so `make reproduce` stays key-free. The pickle is gitignored-by-omission for now; commit it only if retraining proves slow.
39. **A daily-quota 429 stops the batch; it is neither retried nor downgraded.** First plumbing run hit gpt-oss-120b's free-tier limit of 200k tokens per day at silver label 150/200; three calls then fell back to 20B and were cached under the 120B key (rows deleted by hand). `llm.DailyQuotaExceeded` now surfaces immediately with a resume hint; per-minute 429s still retry and fall back. Consequence for planning: one full golden-set pass (200 rows x up to 3 calls x ~1k tokens) is roughly the whole daily allowance, so silver labelling, the golden run, and re-runs after prompt changes must land on different days or the cache does the work.
40. **Silver labels for the simple baseline come from FALLBACK_MODEL (gpt-oss-20b), reusing any label already cached from PRIMARY_MODEL.** `baselines.simple.silver_label` first probes the primary cache with a call_fn that raises on a miss, then labels on the fallback. The split (`primary_cached` vs `fallback`) is written to `eval/results/simple_silver.json` and surfaces in summary.json under `silver_labels`. Rationale: a baseline should not compete with the system for the 120B daily quota. Caveat: the enrich prompt was rewritten the same day (decision #41), which changes every cache key, so in practice the earlier 147 primary-cached labels no longer match and all 1,000 land on 20B.
41. **Enrich system prompt compacted from 986 to 621 tokens** (tiktoken o200k_base, the closest public ruler for gpt-oss; `scripts/measure_prompt.py`). Changes: one example per intent (the shorter of the two), a one-line schema with literal defaults instead of a pretty-printed example, the rules block as one paragraph, and tighter definition wording in `taxonomy.py` with the same scope (the trip definition had duplicated "wrong route" after decision #30's addition). The 550 target was not reached: the last ~70 tokens would mean dropping the examples (~110 tokens) or narrowing definitions, both of which change classification behaviour. Every enrich cache key changed with the prompt; the earlier `suggested_intent` pass and the 147 silver labels from the old prompt are dead cache rows.
42. **Judge model is `gemini-3.5-flash-lite`.** First live judge call on 2026-09-12 returned 404: `gemini-2.5-flash-lite` is no longer available to new API users, and Google's error names 3.5-flash-lite as the replacement. Still Flash-Lite, still a different family from the drafter, so the design reason for the judge choice holds.
43. **UI built on 2026-09-12 with rule 10 half met.** `eval/results/` exists, but `make reproduce` has not been timed with all three systems because the Groq daily quota blocked the "ours" run. The frontend is deliberately minimal (Vite + React 18 + Tailwind 4, two tabs, no router or state library) and reads only `POST /chat`, `GET /escalations`, `POST /escalations/{id}/resolve`, so it does not constrain anything the eval still needs to change.
44. **Trace page (2026-09-13).** Every `run()` builds a `trace` dict (shape: `docs/TRACE_SPEC.md`) and stores it as JSON in a new nullable `tickets.trace` column; `init_db` adds the column with `ALTER TABLE` when an older `app.db` lacks it, so the 56 pre-existing tickets show "no trace" rather than breaking. Per-step LLM accounting comes from `cache.LAST_CALLS`, a per-request list of `{model, hit, messages, response}` that `cached_llm` appends to and `run()` clears at the start (process-wide like `cache.STATS`, decision #25). `rules.explain()` evaluates every rule even after an earlier one fired (they are pure, so this is free) and adds a 0..1 `margin` so the UI can name the two rules closest to firing; `evaluate()` is untouched and still short-circuits. `draft()` was split into `draft_raw()` + `postprocess_with_notes()` so the trace can show raw next to final with the post-processing steps that changed it; the text the customer gets is byte-identical. Baseline predictions (`predict_one`) are computed after `latency_ms` is measured and stored under `trace["baselines"]`, so eval latencies are unaffected. `X-Cache-Only: 1` on `POST /chat` is honoured through a `ContextVar` in `cache.py`, not by mutating `os.environ`: sync endpoints run in a thread pool, and an env flip would leak into a concurrent normal request. A miss under the header is a 409, never a network call.
45. **Trace tokens are a chars/4 estimate, labelled as such.** `llm_cache` stores only the response text, so real `usage` is unavailable on cache hits, and tiktoken's `o200k_base` needs a network download on first use (it hung for two minutes on this machine with no cache), which would break `make reproduce` and the tests. `pipeline/pricing.py` divides characters by four and stamps `token_counter: "chars/4 estimate"` on every trace; the report must not present these as measured. List prices there are Groq pay-as-you-go as of 2026-09-13 (gpt-oss-120b $0.15/$0.60, gpt-oss-20b $0.075/$0.30 per 1M in/out); the free tier pays 0, so `estimated_paid_cost_usd` answers "what would this have cost", nothing more. Swapping in stored usage later needs one extra `llm_cache` column and no UI change.
46. **`sample_golden.py --suggest` fills five `suggested_*` columns, never the ground truth.** `suggested_sentiment`, `suggested_urgency` come from the enrichment; `suggested_escalate` (`True`/`False`) and `suggested_reason` (rule name or `none`) from `rules.evaluate` on that enrichment, so the labeller sees exactly what the system would do. Only rows with an empty suggested column are enriched, and an existing `suggested_intent` is kept rather than overwritten (the rerun reports how often the fresh enrichment disagrees with it; escalate/reason follow the fresh enrichment). Progress is saved every 20 rows and on a cache miss or daily-quota stop, so the command can be rerun until no blanks remain. Ground-truth columns, `ideal_reply_notes` and `labeller` are never written (PROJECT_GUIDE.md rule 2). The enrich calls use the same cache keys as `make eval`, so this pass also pre-warms the eval cache; on 2026-09-13 only 3 rows were cached under the current prompt (decision #41), so the run spent most of that day's 120B quota. (The golden set was 150 rows even at this point — see #48; the file has never held more than that.)
47. **`Entities.amount` accepts currency strings.** During the first `make eval` silver-labelling pass the enricher returned `"amount": "£4.25"` for one pair; Pydantic rejected it and the retry (decision #14) recovered at the cost of a second call. A `mode="before"` validator now strips everything but digits and dots, so "£4.25", "$13" and "Rs 555" parse first time. The prompt was deliberately not changed: any wording change alters every enrich cache key, and the golden-set enrichments cached on 2026-09-13 would become dead rows. Cached responses containing a currency string now parse too, since validation happens after the cache.
48. **Golden set trimmed to the 150 labelled rows (g001–g150) on 2026-09-13.** The labeller stopped at 150; rows g151–g200 were dropped from `data/golden_set.csv` (a 200-row backup was kept outside the repo, and the unlabelled 200-row version is in git history). Their tweets stay out of the retrieval corpus, so the leakage check still passes and the corpus is unchanged. `stats.json` records rows=150. The first `make eval` on real labels ran trivial (150/150) and stopped at silver label 590/1000 with the gpt-oss-20b daily quota exhausted; the system run was not attempted because the safety check uses the same model and would have failed closed on every draft. Rerun `make eval` after the quota reset; the 590 silver labels and all 150 enrichments are cached.
